# Repository Guidelines

## Project Structure & Module Organization
Everything meaningful sits in `src/`: thin localized route wrappers in `src/pages/` (Polish at the root, English under `src/pages/en/`), shared page templates in `src/components/pages/`, reusable UI in `src/components/`, typed content/data in `src/data/`, shared contracts in `src/types.ts`, utilities in `src/utils/`, and Tailwind tweaks in `src/styles/global.css`. Keep static assets and meta files in `public/`. The `dist/` directory is generated by the build and must stay untouched.

## Build, Test & Development Commands
`npm install` hydrates dependencies. Use `npm run dev` for hot-reload development on `localhost:4321`, `npm run build` for the optimized bundle, and `npm run preview` to smoke-test that output. `npm run check` invokes Astro Check for TypeScript, Markdown, and accessibility diagnostics. `npm run validate:data` checks route/content invariants, and `npm run validate` runs data validation, Astro Check, and the production build. Reach for `npm run astro <subcommand>` when scaffolding integrations or running CLI utilities.

## Coding Style & Naming Conventions
Stick to two-space indentation. Components stay in PascalCase (`TrainerProfiles.astro`), route files use kebab-case to mirror URL slugs (`o-nas.astro`), and data-driven text belongs in `src/data` rather than inline markup. Prefer Tailwind utilities; only add custom CSS in `global.css` with narrowly scoped selectors. Extend the types in `src/types.ts` before evolving data payloads, and keep imports path-relative inside `src/` to work with Vite aliases.

## Testing Guidelines
There is no standalone unit-test runner yet, so treat `npm run validate` plus `npm run preview` as the baseline gate before every push. Manually click through the home hero, schedule widget, and trainer grid in both locales to ensure data alignment. When experimenting with new data structures, add assertions to `scripts/validate-data.ts` and document any missing automated coverage in your PR.

## Commit & Pull Request Guidelines
Commits follow the imperative, title-cased style seen in `git log` (“Add reusable SocialMeta component…”). Keep each commit focused, referencing affected components or data files when relevant. PRs need a problem statement, implementation summary, manual test notes, and—when UI shifts—before/after screenshots. Link issues, request review from content owners when JSON changes, and confirm both `pl` and `en` routes were exercised locally.

## Localization & Content Tips
Astro’s `i18n` defaults to Polish without a prefix, so only English routes require `/en/...` paths. Keep route mappings and page metadata in `src/data/site.ts`, and keep class IDs stable in `src/data/classes.ts` because components rely on them as keys. If locale-specific layout diverges, create a dedicated shared template variant under `src/components/pages/` rather than branching heavily inside route files.
